# 065103 Packet — SPH Announce and Configuration Snapshot

## Conclusion

`065103` is best understood as the inverter's **announce record**.  For the
SPH represented by these captures, the large inverter-to-server form contains
an identification/configuration snapshot made from three ranges of Modbus
function-03 holding registers.  It is not another live-production telemetry
packet like `065104`.

This interpretation is unusually well supported:

- Grott explicitly calls `5103` an `announce record` in `grottconf.py`.
- Grottserver handles an incoming type `03` by recording the logger/inverter
  association, acknowledging it, and queuing a clock-setting command.
- Every complete 829-byte body found here contains the exact range markers
  `0..124`, `1000..1124`, and `1125..1249`.
- Those are exactly the function-03 ranges that
  `grott/documentatie/registers.md` lists for an SPH.
- Values at the corresponding positions decode as documented holding-register
  content: enable flags, power limits, firmware strings, inverter identity,
  the inverter clock, grid-protection settings, operating priority and battery
  configuration.

The word “announce” describes the packet's role in connection setup.  The body
is much richer than an identity announcement: it announces the device while
also supplying its current configuration and firmware information.

## Forms seen on the wire

The key is header bytes `major=0x06, n0=0x51, n1=0x03`.  Key alone is not
enough to describe the message because both directions use it.

| Direction | Decoded body | Interpretation |
| --- | ---: | --- |
| inverter to server | 829 bytes | announce/configuration snapshot |
| server to inverter | one byte `00` | successful acknowledgement |
| server to inverter | one byte `02` | likely request or retry trigger for the announce record |

The `00` interpretation is confirmed by Grottserver's generated response to an
incoming `03` record.  The `02` interpretation is inferred from ordering: it
often precedes an 829-byte record by a few seconds.  It should not be decoded
as a register snapshot.

Repeated 829-byte bodies within a connection are normally byte-for-byte
identical.  Some captures contain a sequence of retries followed by the `00`
reply, explaining why raw packet counts substantially overstate the number of
distinct announcements.

## Body layout

As with `065104`, offsets below are offsets into `Packet.body`, after decryption
and removal of the CRC.

```text
body[0..30]     logger serial, NUL padded
body[30..60]    inverter serial, NUL padded
body[60..66]    six-byte announce prefix; usually zero, meaning unresolved
body[66]        03, apparently the record-type marker

body[67..69]    start register: 0
body[69..71]    end register:   124
body[71..321]   holding registers 0..124 (125 big-endian u16 words)

body[321..323]  start register: 1000
body[323..325]  end register:   1124
body[325..575]  holding registers 1000..1124

body[575..577]  start register: 1125
body[577..579]  end register:   1249
body[579..829]  holding registers 1125..1249
```

The size follows directly from that structure:

```text
60-byte serial header + 7-byte record prefix
+ 3 * (4-byte range header + 125 * 2-byte register) = 829 bytes
```

For direct extraction:

```text
register 0..124:       body offset = 71  + 2 * register
register 1000..1124:   body offset = 325 + 2 * (register - 1000)
register 1125..1249:   body offset = 579 + 2 * (register - 1125)
```

Each register is an unsigned 16-bit big-endian word.  Some documented values
span two words or store two ASCII characters per word, so field-specific
decoding is still required.

The six bytes at `body[60..66]` are zero in 2,263 of the 2,315 complete
records.  The other 52 begin `00 32` and retain a capture-specific four-byte
suffix, including across retries.  They are not a valid calendar value like
the six-byte date in `065104`; their purpose remains unresolved.  Byte 66 is
`03` in every complete record.

## What appears to be in the registers

The bundled Growatt Modbus document and Grott's register notes provide the
following useful interpretation.  These names and scales come from incomplete
vendor documentation and reverse engineering, so they should be treated as
candidate semantics rather than a promise that every firmware uses them
identically.

| Register(s) | Candidate content | Evidence in these captures |
| --- | --- | --- |
| `0` | inverter/BDC on-off state | always `1` |
| `3` | maximum active-power percentage | always `100` |
| `4` | maximum reactive-power percentage | always `100` |
| `5` | power-factor setting, scaled by 10,000 | always `10000` |
| `6..8` | rated power and normal PV voltage | stable numeric configuration |
| `9..14` | two firmware version strings | readable ASCII; part changed in March 2026 |
| `15` | LCD language | always `1` (documented as English) |
| `17..21` | PV start voltage, delays and power slopes | stable for the whole series |
| `23..27` | inverter serial number | ASCII and agrees with the identity header |
| `34..41` | manufacturer text | readable ASCII (`New Energy`, padded) |
| `42..44` | fail-safe flag, device type code, tracker/phase type | stable except register `44` after the firmware change |
| `45..51` | year, month, day, hour, minute, second and weekday | tracks the inverter's local clock |
| `52..67` | grid voltage/frequency protection and reconnect limits | plausible scaled voltage/frequency limits |
| `82..87` | firmware build/model text | readable ASCII; changed during the March firmware transition |
| `1008` | packed system-enable flags | alternates between `0x4200` and `0x6200` |
| `1044` | Load/Battery/Grid First priority | always `0`, documented as Load First |
| `1048` | battery-type selector | always `1`; the exact label should be verified against this firmware |
| `1060..1062` | backup/UPS enable, voltage and frequency selections | `1, 0, 0`, consistent with enabled 230 V/50 Hz backup settings |
| `1070..1071` | Grid First discharge rate and stop SOC | always `100` and `5` |
| `1080..1088` | three Grid First time windows and enables | all zero |
| `1090..1092` | Battery First charge rate, stop SOC and AC-charge enable | always `100, 100, 0` |
| `1100..1118` | Battery/Load First schedules and enable flags | mostly zero; register `1109` is consistently `10` |
| `1125..1204` | serial-number space for up to ten battery packs | the first slot contains readable ASCII; later slots are empty here |
| `1244..1249` | battery controller/monitor firmware identifiers | stable ASCII/numeric version data |

Register `1008` deserves caution.  The two observed values differ by bit 13,
which the bundled V1.24 document labels as an enable flag, but the value
switches back and forth over time while almost all other configuration remains
fixed.  It may reflect a scheduled or current enable state rather than a
simple persistent setting.

## Evidence across the capture collection

I scanned all 997 root-level captures, covering 2025-10-27 through 2026-09-21.
The compact Python scanner cannot reassemble a Growatt frame split across TCP
reads, so 75 malformed/partial capture blocks were skipped independently
rather than causing the remainder of their files to be discarded.

The scan found:

- 4,064 visible `065103` frames in 900 captures;
- 2,315 inverter-to-server bodies, all exactly 829 bytes;
- 1,749 server-to-inverter one-byte bodies: 1,135 `00` and 614 `02`;
- at least one complete 829-byte record in 887 captures; and
- 868 distinct 829-byte bodies, with most duplication caused by retries.

All 2,315 complete bodies had the same three range headers and therefore the
same 375-register shape.  Of those 375 register positions, only 15 changed at
all across the entire collection:

- seven clock registers (`45..51`);
- firmware/build-related registers `13`, `14`, and `83..86`;
- tracker/phase register `44`; and
- packed flag register `1008`.

Every other register was byte-for-byte stable (the unresolved prefix at
`body[60..66]` varied separately).  Around 2026-03-13 the firmware
strings, register `44`, and part of the build identifier changed together;
another build-string change appeared on 2026-03-16.  That coherent transition
is further evidence that the packet is a configuration/identity snapshot and
not sampled operating telemetry.

## Relationship to `065104`

Both large packets use the same 60-byte identity header and then encode
16-bit big-endian register data.  Their final byte distinguishes the purpose:

- `...03` carries function-03-style holding/configuration registers and is
  sent as an announcement, normally around connection setup.
- `...04` carries function-04-style input/live-data registers and repeats as
  operational telemetry.

This also explains why Grott's generic telemetry fallback accepts `04` (and
buffered `50`) but not `03`: Grott handles `03` as connection announcement
state rather than publishing it as live measurements.

## Remaining uncertainty

The packet role and range structure are high-confidence.  Individual register
names are less certain because Growatt register maps vary by inverter family
and firmware, and even the bundled documentation contains incomplete or
inconsistent scales.  Before exposing a setting in `src/tables.rs`, its value
should be checked against the inverter UI/API or changed deliberately and
observed in a new announce record.  Configuration registers should not be
written merely on the strength of this decoding.
